10. Merging, rebasing and conflicts

Merge

Toolbar Merge (or right-click a branch → Merge into …). Options: always create a merge commit (--no-ff), or squash everything into one uncommitted change.

Merge one branch into several (Merge to many)

Use this when the same change must reach several branches, for example a bug fix that belongs in release-1, release-2, release-3 and release-4. You do it once instead of four times, and you see the conflicts before anything changes.

  1. More → Merge into several branches… (or right-click a branch → Merge this into multiple branches…).
  2. Choose. Merge from is the current branch unless you change it. Tick the branches that should receive it (Select all is there too), then Next: check for conflicts. Nothing has changed yet.
  3. Review. Treeline test-merges into every branch without touching your files and shows one result for each: Fast-forward, Clean merge, Already up to date, Conflict (with the files that conflict) or Cannot merge (for example the branch is checked out in another worktree). Safe branches are ticked; conflicting ones cannot be ticked. Press Merge into N branches.
  4. Done. You get one line per branch. Nothing is pushed: push each branch yourself afterwards.

How the merges are made: a branch that is not checked out is updated directly, without switching to it, with a merge commit named Merge branch 'X' into Y. The branch you have checked out gets a normal merge, so commit or stash your uncommitted changes first if Git refuses. Every branch is checked again right before merging, and one that has become conflicting is skipped, never forced.

A branch with conflicts. Press Resolve… next to it. The dialog hides, Treeline checks that branch out and starts the merge, and you resolve the conflicts in File status as usual (see Conflicts below) and press Continue. A bar at the bottom of the window then offers Resume: Treeline re-tests every branch, and the one you finished shows as Already up to date. Cancel closes everything.

Reuse my resolution. The first time you press Resolve…, Treeline turns on Git's rerere (“reuse recorded resolution”) for this repository, which is a setting in its .git/config, and tells you so. Git then remembers how you resolved the conflict. Afterwards, branches that still conflict get Apply my earlier resolution to N. For each one Treeline checks the branch out, lets Git replay your fix, and commits only if every conflict was covered; otherwise it aborts and leaves the branch untouched and says so. This needs a clean working tree and returns you to the branch you were on. It works when the conflict is identical, which is typical for the same fix going to several release branches.

“Merged, but changes dropped.” If a merge ended up with a branch's own version of a file (for example you chose Keep ours where you should have combined), the change you wanted is missing there. Treeline checks this when you press Resume and after replaying a resolution, and shows a red banner naming the branch and files. To fix it, Revert that merge commit and merge again.

Rebase

Right-click a branch → Rebase current onto this… replays your commits on top of another branch for a linear history. Only rebase commits you haven't shared.

Interactive rebase (tidy up recent commits)

Right-click a commit in History → Interactive rebase from here…. For each commit choose Pick, Reword (edit the message), Edit (pause to amend it), Squash (merge into the one before, combining messages), Fixup (merge, discarding its message) or Drop. Use the arrows to reorder (newest on top). Uncommitted changes are stashed and restored automatically. Merge commits aren't listed (a rebase flattens them).

Conflicts

A conflict means both sides changed the same lines. The operation pauses — nothing is lost.

  1. A yellow banner (“Merge in progress …”) appears in File status; conflicted files are listed under Conflicts.
  2. Click a conflicted file. For each conflict choose Use ours, Use theirs, Both or Both (reversed) — or edit the Result box by hand.
  3. Click Mark resolved (enabled when every conflict is decided). Repeat for each file.
  4. When no conflicts remain, press Continue in the banner. Abort cancels and restores the state from before.

Hover any button in the resolver for a hint that says exactly what it does and what it throws away. The hints and the column headings (Ours · release-4, Theirs · bugfix) name the real branches. Use this result and Mark resolved stage the file but do not commit; you commit the merge afterwards with Continue.

“Filled in from your earlier resolution.” When Git already applied a resolution it remembered (see Reuse my resolution above), the file has no conflict markers although it is still unresolved. The resolver then shows the result and a Use this result button. Review it and press that. Keep ours or Keep theirs would throw the remembered resolution away.

Ours = the branch you are on; theirs = the one being merged in (for a rebase these are swapped in meaning, which is normal Git behaviour). If one side deleted the file you get Keep ours / Keep theirs instead.

Cherry-pick, revert, reset

  • Cherry-pick copies one commit onto the current branch.
  • Revert makes a new commit that undoes an earlier one (safe for shared history).
  • Reset moves the branch pointer — see section 12.
